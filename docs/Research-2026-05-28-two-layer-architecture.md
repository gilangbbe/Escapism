# Two-layer architecture: Generator AI \u2192 Simulator runtime

*Design memo \u2014 2026-05-28.* Companion to
[Research-2026-05-28-simulation-redesign.md](Research-2026-05-28-simulation-redesign.md).

**Goal.** Make every escape-room scenario in this project the output of a
Generator LLM (Layer 1), consumed by the Simulator we are building today
(Layer 2). Every world, every puzzle, every NPC \u2014 procedurally produced,
infinitely varied, and **guaranteed solvable** without human authoring.

---

## 1. The hard problem

Procedural escape-room generation is *qualitatively* harder than
procedural dungeon or quest generation because:

1. **Solvability is a global property.** A maze just needs a path. An
   escape room needs a *chain of inferences* the player can actually
   draw from the in-game evidence \u2014 every effect must have a discoverable
   cause, every key must be reachable before its lock.
2. **Difficulty is a curve, not a number.** Good rooms ramp:
   trivial \u2192 medium \u2192 hard \u2192 climax. Random generation flatlines.
3. **Theme coherence.** A pirate brig in 1721 cannot contain a USB drive.
   The Generator has to respect a *style bible* the Simulator never
   knows about.
4. **The Simulator must trust the contract.** Anything the Generator
   emits that the Simulator can\u2019t parse, validate, or execute becomes
   silent runtime drift.

So the question is really three questions:

- How does Layer 1 emit content that Layer 2 *cannot* misinterpret?
- How does Layer 1 prove the room is **solvable** before handing it over?
- How does Layer 1 stay **on-theme** and **on-difficulty** without
  human curation?

## 2. Prior art

Five lines of research are directly relevant.

### 2.1 Constructive PCG with formal solvers

- **Smith & Mateas, *Answer Set Programming for Procedural Content
  Generation*, 2011.** Levels are generated by ASP solvers under
  hard constraints \u2014 the solver guarantees solvability by construction.
- **Bhaumik et al., *Solving Escape Room Puzzles with Constraint
  Programming*, 2020.** Models escape rooms as CSPs (Constraint
  Satisfaction Problems); ensures every puzzle has exactly one solution.
- **Cooper, *Sturgeon* (2022).** A constraint-based level generator that
  uses SAT to prove a generated level is winnable.

Takeaway: a classical planner / SAT solver next to the LLM is the
state-of-the-art way to *prove* generated content is solvable.

### 2.2 LLM-as-author with verification

- **MarioGPT (Sudhakaran et al., 2023):** LLM generates Mario levels;
  a separate A* agent verifies playability; unplayable outputs are
  rejected and regenerated.
- **WordCraft / Word2World (Hu et al., 2024):** LLM emits a structured
  world; a symbolic checker validates room connectivity, item
  reachability, and goal achievability before the world ships to a
  player.
- **GPT Dungeon Master experiments (various 2023\u20132024 papers):** all
  converged on \u201cLLM proposes \u2192 validator filters \u2192 reprompt on
  failure.\u201d

Takeaway: the LLM is almost never trusted on its own \u2014 it is paired
with a deterministic checker that owns the *truth* of \u201cis this valid?\u201d.

### 2.3 Quest / mission generation (game industry)

- **Diablo III / IV bounty system:** templated quest slots filled at
  runtime from a constrained vocabulary.
- **No Man\u2019s Sky / Dwarf Fortress:** generative *worlds* with
  hand-authored *systems*; the systems guarantee internal consistency.
- **AI Dungeon (2019\u20132024):** the cautionary tale \u2014 zero validation
  layer means infinite freedom and no enforceable rules.

Takeaway: ship the systems by hand; generate the *parameters* of
those systems. Don\u2019t let the LLM invent the engine.

### 2.4 Drama / narrative managers

- **Mateas & Stern, *Fa\u00e7ade* (2003):** an offline-authored drama
  manager dynamically reorders beats at runtime to hit a target arc.
- **Riedl & Bulitko, *Interactive Narrative*, 2013** (survey): formal
  story planners that interleave with player actions.

Takeaway: it pays to separate *content generation* (one-shot, offline)
from *story management* (online, reactive). For us: Layer 1 = content;
Layer 2 = drama manager + simulator.

### 2.5 LLM agent collaboration patterns

- **Multi-agent debate / critic\u2013generator pairs (Du et al. 2023, Madaan
  et al. 2023):** one LLM proposes, another LLM critiques. Iterate.
- **Self-Refine, Reflexion, ChatDev:** all use *adversarial* loops
  between two LLM roles to drive quality up without humans.

Takeaway: the Generator should not be a single call. It should be a
small **society of LLM roles** (Writer, Puzzle Designer, Critic, QA
Player), each constrained to one job.

## 3. Architecture: three layers, not two

The user described two layers. The robust shape is three.

```

\u2502  LAYER 1  \u2014  GENERATOR (offline, one-shot per scenario)             \u2502
\u2502                                                                      \u2502

\u2502   \u2022 Setting Writer   (theme, era, locations, NPCs)                  \u2502
\u2502   \u2022 Puzzle Designer  (item graph, locks, recipes, puzzles)          \u2502
```

validation, it is immutable for the run \u2014 the simulator never sees the
generator and the generator never sees the simulator's state.

## 4. Layer 1 in detail

### 4.1 The scenario bundle (the contract)

Every generated scenario is a single directory:

```
scenarios/<id>/
  manifest.json          # theme, era, difficulty, version, seed
  game.jsonl             # corpus docs (lore, rule, location, item, npc,
                         # hint, objective, puzzle, recipe)
  world_initial.json     # starting WorldState snapshot
  solver_proof.json      # the canonical solution path (verified by Solver)
  qa_report.json         # QA Player's blind walkthrough log
```

The manifest pins the JSON-Schema version of every file. The simulator
refuses to load a bundle whose `schema_version` it does not implement.
**No backward compat hacks** \u2014 a generator from 2027 cannot break a
simulator from 2026.

### 4.2 The generation pipeline (a DAG of LLM + tool calls)

```
[user prompt or random seed]
        \u2502
        \u25bc
  1. SettingWriter LLM  \u2192 setting.json
        \u2502   ("brig of a 1721 pirate ship", "haunted lighthouse 1890",
        \u2502    "abandoned space station 2189"). Locations + NPC sketches +
        \u2502    win conditions + tone bible.
        \u25bc
  2. PuzzleDesigner LLM  \u2192 puzzle_graph.json
        \u2502   Emits an ITEM/STATE DAG: nodes = inventory items + object
        \u2502   states; edges = puzzles ("rope + knife \u2192 rope_grapple";
        \u2502   "rope_grapple on hal_keyring requires hal=drugged \u2192 keyring").
        \u2502   Root: initial inventory + initial discovered items.
        \u2502   Sink: every win condition's required state.
        \u25bc
  3. Solver (deterministic Python)
        \u2502   Translates puzzle_graph to PDDL or a custom BFS over states.
        \u2502   Verifies: (a) every win-condition state is reachable from
        \u2502   start, (b) shortest path length is in [DIFF_MIN, DIFF_MAX],
        \u2502   (c) no "dead items" (items never consumed), (d) no "lonely
        \u2502   keys" (states reachable that lead nowhere).
        \u2502   If FAIL  \u2192 emit precise complaint; loop back to PuzzleDesigner.
        \u25bc
  4. NarrativeEditor LLM  \u2192 game.jsonl
        \u2502   Wraps each node/edge in prose using the tone bible:
        \u2502   item.<id>.text, location.<id>.text, puzzle.<id>.title,
        \u2502   hint tiers 1/2/3 for every puzzle.
        \u25bc
  5. Critic LLM (no tool access; reads-only)
        \u2502   Scores: theme coherence, anachronism, tonal drift, prose
        \u2502   quality, hint subtlety. Below threshold \u2192 loop to NarrativeEditor.
        \u25bc
  6. QA Player LLM (uses the actual Simulator, mock-LLM-free)
        \u2502   Spins up a sandbox Simulation with this bundle, plays as
        \u2502   a real Player agent with no privileged info, logs every
        \u2502   stuck-tick and hint use. Friction metrics: max_streak_same_action,
        \u2502   hints_used, ticks_per_phase. If any phase ticks > DIFF_MAX*2,
        \u2502   loop back to Solver (the puzzle is technically solvable but
        \u2502   unfair).
        \u25bc
  7. Freeze bundle  \u2192  scenarios/<id>/
```

Every step has a **machine-checked output** before the next step runs.
The LLM never gets to mark its own homework.

### 4.3 The puzzle graph: a STRIPS-like DSL

This is the key insight. The PuzzleDesigner does **not** emit prose; it
emits a planning problem. Example fragment:

```json
{
  "items": ["folding_knife", "rope_coil", "herbs", "vial", "lantern",
            "sleeping_draught", "rope_grapple", "hal_keyring"],
  "object_states": {
    "hal_mug": ["full_rum", "tainted_drunk", "empty"],
    "rope_coil": ["coiled", "rigged"],
    "cell_door": ["locked", "open"],
    "hal": ["awake", "asleep_drunk", "drugged_deep_sleep"]
  },
  "initial": {
    "inventory": ["folding_knife", "ledger_fragment"],
    "object_state": {"hal_mug": "full_rum", "hal": "awake",
                     "cell_door": "locked", "rope_coil": "coiled"}
  },
  "goal": {"current_location": "lower_decks",
           "objectives": {"escape_brig": "complete"}},
  "operators": [
    {"id": "puzzle.brew_draught",
     "trigger": {"verb":"COMBINE","ingredients":["herbs","vial","lantern"]},
     "pre": {"inventory_has":["herbs","vial"],
             "object_state":{"lantern":"focused"}},
     "eff": {"inventory_add":["sleeping_draught"],
             "inventory_remove":["herbs"]}},
    /* ... one per puzzle ... */
  ]
}
```

This is literally a PDDL problem in JSON clothes. The Solver runs BFS
(or Fast Downward via a shell-out) and either returns a plan of length
N or proves unsolvability. Both outcomes are useful: solvable rooms
ship; unsolvable ones go back to the designer with the unmet
preconditions.

The Simulator already speaks 90% of this dialect (we shipped
`trigger`/`preconditions`/`effects` yesterday). Layer 1 just needs to
produce it.

### 4.4 Difficulty as a tunable

`manifest.json` declares `target_solution_length` and
`target_red_herrings`. The Solver enforces the first; the PuzzleDesigner
adds optional `decoy_items` (items with no operator that consumes
them but plausible-looking prose). The QA Player measures
`tick_overhead = actual_ticks_to_solve / optimal_ticks`; rooms with
overhead > 3 are flagged as unfair and regenerated.

### 4.5 Theme coherence: the style bible

The SettingWriter's first output is a `tone.md`:

```
era: 1721 Caribbean
prohibited_anachronisms: [electricity, plastic, gunpowder_keg_safety,
                          metric_units, modern_idiom]
voice: second-person GM, terse, salt-water imagery
color_palette: rust, brine, lantern-yellow, midnight-blue
```

Every other LLM in the pipeline gets `tone.md` in its system prompt.
The Critic\u2019s sole job is to flag violations.

## 5. Where the existing Layer-2 work plugs in

Everything we built in Phase 4 is exactly what the runtime needs:

| Layer-2 component        | What the bundle provides                  |
|---|---|
| `ClueStore`              | `game.jsonl` (already the format!)        |
| `WorldState.load(...)`   | `world_initial.json` (already the format!)|
| `puzzle_validator.py`    | puzzle docs with `trigger/pre/eff` (\u2713)   |
| `Salty` hints            | `hint` docs at tiers 1/2/3 (already)      |
| `Reflector`              | works unchanged                           |
| Affordance menu (Stage 1 of yesterday\u2019s memo) | **required** \u2014 menu is computed from the bundle, not invented by the LLM |

The migration from \u201chand-authored Black Vesper\u201d to \u201cgenerated\u201d is
essentially: move `data/` to `scenarios/black_vesper/` and point the
loader at a CLI flag (`SCENARIO=black_vesper python -m server`). No
code change in the Simulator beyond the path indirection. The Black
Vesper bundle then becomes the **regression fixture** for every
generator change forever after.

## 6. Implementation plan (phased)

### Phase A \u2014 freeze the contract (no generator yet)

1. Define JSON Schemas for every doc kind in `schemas/v1/`:
   `meta.schema.json`, `location.schema.json`, `item.schema.json`,
   `puzzle.schema.json`, `recipe.schema.json`, `hint.schema.json`,
   `world_initial.schema.json`, `manifest.schema.json`.
2. Move `data/game.jsonl` + `data/world_initial.json` into
   `scenarios/black_vesper/` and add a `manifest.json` declaring
   `schema_version: 1`.
3. Write `scripts/validate_scenario.py` that runs JSON-Schema against
   every file and prints a clean report.
4. Add a CI test that validates every bundle in `scenarios/`.

This makes the contract *real* without writing any LLM code yet.
Black Vesper continues to work; future bundles only need to satisfy
the schemas.

### Phase B \u2014 the Solver

1. `tools/solver/state_search.py`: pure-Python BFS over the
   `{inventory, object_state, npc_state, location}` tuple, using the
   operator list from the puzzle docs. Returns the plan or
   `Unsolvable(reason)`.
2. CLI: `python -m tools.solver scenarios/black_vesper` \u2192 must print
   a 13-step plan that matches our mock smoke. This is a powerful
   regression test for free.
3. Bonus: emit `solver_proof.json` into the bundle so the simulator
   can show "Optimal: 13 ticks" in the HUD.

### Phase C \u2014 affordance engine (yesterday\u2019s Stage 1)

Required for two reasons: (a) makes the Player robust to generated
scenarios with unfamiliar item names; (b) is the basis for the QA
Player. Implementation already designed in yesterday's memo.

### Phase D \u2014 the Generator pipeline (LLM)

1. `tools/generator/setting_writer.py` \u2014 one LLM call, emits
   `setting.json` (locations + NPC sketches + tone bible).
2. `tools/generator/puzzle_designer.py` \u2014 LLM with the setting as
   context, emits `puzzle_graph.json` in the DSL above. Constrained
   decoding (Ollama `format=json` + schema in prompt).
3. `tools/generator/narrative_editor.py` \u2014 LLM expands every node to
   prose, emits `game.jsonl`.
4. `tools/generator/critic.py` \u2014 LLM reads bundle, returns
   `{accept: bool, complaints: [...]}`. Loop with NarrativeEditor.
5. `tools/generator/qa_player.py` \u2014 instantiates a `Simulation` with
   the bundle, runs N ticks with the real Player agent, returns
   metrics.
6. `tools/generator/orchestrator.py` \u2014 wires the DAG, handles
   retries and bundle freezing.

### Phase E \u2014 deployment & UX

- `POST /api/scenarios/generate { theme, difficulty }` \u2192 returns a
  job ID; pipeline runs in the background; client polls. On success
  the new scenario id appears in a dropdown.
- `POST /api/runs/new { scenario_id }` \u2192 start a Simulation against
  that bundle.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Generator emits unsolvable rooms | Solver step is **mandatory**; loop on failure |
| Generator emits boring rooms | Critic + QA Player metrics; minimum solution length; minimum red-herring count |
| Generator hallucinates a state name the simulator doesn\u2019t recognise | JSON-Schema validation at load time; `object_state` values restricted to those declared in `puzzle_graph.json` |
| Generated prose mentions items the puzzle graph doesn\u2019t support | NarrativeEditor's prompt is *constrained* to the item/state set; Critic flags references to undeclared entities |
| Two LLMs disagree about an item\u2019s identity (e.g. "lantern" vs "oil lamp") | Puzzle DSL uses canonical IDs; NarrativeEditor must reference items by `{{item:lantern}}` placeholders that are post-processed |
| Generation cost (multiple LLM calls per scenario) | Cache aggressively per-stage; pipeline is one-shot per scenario; bundles are reusable |
| Different generator versions produce subtly incompatible bundles | `schema_version` in manifest; simulator refuses unknown versions; ship migrations explicitly |
| QA Player loops forever | Hard tick cap; failure to solve in `5 \u00d7 optimal` is a fail |

## 8. Why this is the right shape

1. **The Simulator becomes content-agnostic.** Everything Layer 2 needs
   is already a parameterised piece of data. We delete `data/` and gain
   infinite scenarios.
2. **The Generator can be entirely offline.** No latency pressure
   during a run \u2014 a bundle is generated once, played many times.
3. **The Solver makes solvability a build-time property, not a
   prayer.** This is the single most important architectural choice.
4. **The QA Player closes the loop using the *real* simulator** \u2014 if a
   change to Layer 2 breaks a bundle, the QA Player catches it before
   any human plays it.
5. **Multi-agent (Phase 5) drops in cleanly.** A bundle declares
   `agents: [{id, persona, start_location, start_inventory}]`; the
   puzzle DSL gains `requires_agents: [a, b]` operators; the Solver
   adapts (it's now a multi-agent planning problem, well-studied).
6. **Generator can itself be LLM-generated.** Once the Solver and the
   DSL are in place, future improvements are mostly prompt-engineering
   on the generator roles, not architectural work.

## 9. Smallest end-to-end demo (one weekend)

The leanest possible proof of the architecture:

1. Phase A done (schemas + bundle layout + Black Vesper migrated).
2. Phase B done minimally (BFS solver that confirms Black Vesper
   solves in 13).
3. Phase D *only* the puzzle-graph step \u2014 prompt the LLM with
   `"theme: lighthouse keeper trapped on a stormy night"`, get a
   `puzzle_graph.json`, run the solver, retry up to 3 times.
4. Hand-write the NarrativeEditor *as a template* (not an LLM yet) to
   wrap the graph in stock prose.
5. Run the simulator against the new bundle. If Mira (or
   "the Keeper") escapes, the architecture works.

Everything else \u2014 Critic, QA Player, generation UX, theme bibles \u2014
is incremental polish.
